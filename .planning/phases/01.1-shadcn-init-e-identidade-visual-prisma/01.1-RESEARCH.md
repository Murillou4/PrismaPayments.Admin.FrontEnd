## Summary

Esta fase fecha o "shadcn gap" da Fase 1: o `components.json` nunca foi gerado, então nenhum componente shadcn foi instalado. A Fase 1 entregou os widgets em CSS inline puro (inline styles em Svelte). Esta fase inicializa shadcn-svelte (que já usa bits-ui como primitiva subjacente — o mesmo bits-ui v2.16.3 já instalado), instala o conjunto completo de componentes necessários para as fases 2–8, e migra todos os widgets existentes para usar essas primitivas internamente enquanto aplica a identidade visual Prisma.

O ponto crítico é o mapeamento de CSS variables: shadcn-svelte usa variáveis como `--primary`, `--background`, `--accent` etc. — estas devem ser sobrepostas em `src/app.css` para apontar para os tokens Prisma já existentes (`--color-brand-magenta`, `--color-background`, etc.), não o contrário. O projeto usa Tailwind v4 via `@tailwindcss/vite` (sem PostCSS), e shadcn-svelte a partir da versão `@latest` (1.2.3 no npm registry) suporta Tailwind v4 nativamente com este setup.

A migração dos widgets é conservadora por design (D-06): paths de import não mudam, APIs de props não mudam — apenas os internals adotam primitivas bits-ui com estilização via Tailwind classes mapeadas para tokens Prisma.

**Primary recommendation:** Inicializar shadcn-svelte com `baseColor: zinc` (o mais próximo do dark neutral), override todas as CSS variables no `app.css`, e migrar widgets preservando a API de props Svelte 5 existente.

### Pattern 1: CSS Variable Override no app.css (Tema Prisma)

**What:** shadcn-svelte espera variáveis como `--primary`, `--background`, `--accent`, `--border`, `--ring`. Em vez de aceitar os defaults cinza, declaramos overrides em `app.css` usando os tokens Prisma já existentes.

**When to use:** Aplicar imediatamente após o init, antes de instalar componentes. Os componentes shadcn renderizados lerão estes valores.

**Mapeamento de variáveis (Claude's Discretion):**
```css
/* Adicionar em src/app.css após @theme block existente */

:root {
  /* shadcn base variables — mapeadas para tokens Prisma */
  --background: var(--color-background);           /* #070707 */
  --foreground: var(--color-foreground);           /* #F6F6FF */

  --card: var(--color-surface);                    /* #0F0F18 */
  --card-foreground: var(--color-foreground);      /* #F6F6FF */

  --popover: var(--color-surface-overlay);         /* #1A1A28 */
  --popover-foreground: var(--color-foreground);   /* #F6F6FF */

  --primary: var(--color-brand-magenta);           /* #FF00FF */
  --primary-foreground: var(--color-background);  /* #070707 */

  --secondary: var(--color-surface-elevated);      /* #141420 */
  --secondary-foreground: var(--color-foreground); /* #F6F6FF */

  --muted: var(--color-surface-elevated);          /* #141420 */
  --muted-foreground: var(--color-foreground-secondary); /* #9090A8 */

  --accent: var(--color-brand-cyan);               /* #01FAFB */
  --accent-foreground: var(--color-background);   /* #070707 */

  --destructive: var(--color-danger);              /* #FF3B5C */

  --border: var(--color-border);                   /* rgba(255,255,255,0.08) */
  --input: var(--color-surface-overlay);           /* #1A1A28 */
  --ring: var(--color-brand-magenta);              /* #FF00FF — focus ring magenta */

  --radius: var(--radius-md);                      /* 12px — padrão para inputs/buttons */
}
```

**Source:** shadcn-svelte theming docs (https://www.shadcn-svelte.com/docs/theming); variáveis validadas na listagem completa de CSS vars do sistema.

### Pattern 2: Widget Migration — Internal Refactor sem quebrar API

**What:** Cada widget mantém sua interface de props Svelte 5 exata. Apenas os internals são substituídos: HTML semântico manual → shadcn component como building block.

**When to use:** Para cada widget em D-05.

**Exemplo — Pagination usando Button:**
```svelte
<!-- ANTES: button com inline style -->
<button style="background: transparent; border: 1px solid var(--color-border)...">←</button>

<!-- DEPOIS: Button do shadcn com variant="outline" -->
<script lang="ts">
  import { Button } from '$lib/components/ui/button/index.js';
</script>
<Button variant="outline" size="icon" disabled={currentPage <= 1} onclick={() => onPageChange(currentPage - 1)}>
  ←
</Button>
```

**Source:** Análise dos widgets existentes (`Pagination.svelte`, `StatusBadge.svelte`, etc.) + shadcn-svelte component API.

**What:** Item ativo na sidebar ganha `border-left: 2px solid var(--color-brand-magenta)` com `box-shadow: inset 2px 0 8px rgba(255,0,255,0.15)` — acento vertical sutil.

**When to use:** Apenas no item `.isActive` do nav em `AdminLayout.svelte`.

### Pattern 4: shadcn-svelte com Tailwind v4 — Init sem PostCSS

**What:** O projeto usa `@tailwindcss/vite` (sem `postcss.config.js`). O CLI `shadcn-svelte@latest init` detecta isso corretamente a partir da versão suportada para Tailwind v4.

**Detalhe crítico:** O `vite.config.ts` já está configurado corretamente:
```typescript
plugins: [tailwindcss(), sveltekit()]
```
`tailwindcss()` deve vir ANTES de `sveltekit()` — já está nessa ordem.

**O init vai perguntar:**
- Style: `new-york` (recomendado para v4) ou `default`
- Base color: escolher `zinc` (neutro escuro mais próximo)
- CSS file: `src/app.css` (o arquivo existente)
- Aliases: confirmar `$lib` e `$lib/components/ui`

**O init NÃO vai criar `postcss.config.js`** se não encontrar um existente e detectar Tailwind v4 via vite plugin.

**Source:** shadcn-svelte migration docs (https://www.shadcn-svelte.com/docs/migration/tailwind-v4); GitHub Discussion #1764.

### Pattern 5: Badge com Variantes por Entidade (Claude's Discretion)

**What:** `StatusBadge.svelte` migra para usar `Badge` do shadcn internamente, mas mantém a lógica de `STATUS_MAP`. As cores continuam sendo aplicadas via `style` attribute inline (valores dinâmicos em runtime — não é possível usar Tailwind classes com valores dinâmicos no Svelte).

**Justificativa:** A decisão do Plan 01-03 foi documentada: "Inline style props for StatusBadge dynamic colors — Svelte scoped CSS cannot use runtime values in class definitions." Isso continua válido. O Badge do shadcn fornece o markup semântico (`<span>` com `data-slot="badge"`) e o Svelte scoped CSS aplica os tokens de cor via `style` attribute.

**Variantes sugeridas por entidade:**

| Status | Cor do texto | Background | Border |
|--------|-------------|------------|--------|
| ACTIVE/APPROVED/RESOLVED | `#00E676` | `rgba(0,230,118,0.10)` | `rgba(0,230,118,0.20)` |
| PENDING/PENDING_REVIEW/OPEN/UNDER_REVIEW | `#FFB300` | `rgba(255,179,0,0.10)` | `rgba(255,179,0,0.20)` |
| SUSPENDED/REJECTED/BLOCKED | `#FF3B5C` | `rgba(255,59,92,0.10)` | `rgba(255,59,92,0.20)` |
| INACTIVE/UNVERIFIED | `#9090A8` | `rgba(144,144,168,0.10)` | `rgba(144,144,168,0.20)` |
| MED (time-sensitive) | `#FF3B5C` | `rgba(255,59,92,0.15)` | `rgba(255,59,92,0.30)` + pulsing left border |

### Anti-Patterns to Avoid

- **Sobreescrever tokens Prisma com CSS vars do shadcn:** Nunca substituir `--color-brand-magenta` — sempre mapear `--primary` PARA `var(--color-brand-magenta)`. Direção: shadcn vars → Prisma tokens.
- **Usar `class` com valores dinâmicos em runtime:** Em Svelte, `class="bg-[{color}]"` não funciona com valores de runtime. Usar `style` attribute para cores dinâmicas (StatusBadge).
- **Instalar tw-animate-css com nome errado:** A lib é `tw-animate-css` (não `tailwindcss-animate`). Import em `app.css`: `@import "tw-animate-css"`.
- **Mudar API de props dos widgets:** D-06 é explícito — feature pages existentes não devem precisar de nenhuma alteração. Verificar todos os callers antes de modificar qualquer interface de prop.
- **Usar `@tailwindcss/postcss` em vez de `@tailwindcss/vite`:** O projeto já usa vite plugin. Não adicionar postcss.
- **Tentar fazer shadcn init com Tailwind v4 via `--tailwind-css-variables-prefix` ou flags obsoletas:** A versão @latest detecta automaticamente.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Modal com focus trap + Escape key | HTML `<dialog>` manual com JS | Dialog do shadcn/bits-ui | bits-ui Dialog gerencia focus trap, Escape, stack de modais, aria-modal — tudo correto |
| Select dropdown acessível | `<div>` com isOpen + z-index hack (atual SelectFilter) | Select do shadcn/bits-ui | bits-ui Select tem keyboard navigation, aria-expanded, portal, dismiss on outside click built-in |
| Tooltip com posicionamento | `position: absolute` manual | Tooltip do shadcn/bits-ui | bits-ui usa Floating UI para posicionamento — colisão com viewport, flipping, etc. |
| Dropdown menu com keyboard nav | Custom `{#if isOpen}` div | DropdownMenu do shadcn/bits-ui | bits-ui DropdownMenu tem roving tabindex, typeahead, sub-menus — correto e acessível |
| Skeleton loader | `animation: pulse` inline | Skeleton do shadcn | Componente consistente com tokens de cor corretos |
| Avatar com fallback | `<img>` com onerror | Avatar do shadcn/bits-ui | bits-ui Avatar gerencia fallback automático para iniciais/ícone |

**Key insight:** bits-ui já está instalado (v2.16.3) — shadcn-svelte é essencialmente um wrapper de geração de código sobre bits-ui. Instalar shadcn gera componentes que usam bits-ui internamente. Não há nova dependência pesada sendo adicionada.

## Common Pitfalls

### Pitfall 1: shadcn init sobrescreve tokens em app.css

**What goes wrong:** O CLI `shadcn-svelte@latest init` adiciona um bloco de CSS variables ao `app.css` com valores padrão do tema selecionado (zinc/slate/etc.). Estes valores sobrescrevem ou conflitam com os tokens Prisma já declarados em `@theme`.

**Why it happens:** O CLI não conhece o design system existente — gera um template padrão.

**How to avoid:** Após o init, revisar o que foi adicionado ao `app.css`. Substituir os valores padrão do shadcn pelos mapeamentos Prisma (Pattern 1 acima). Nunca aceitar os defaults cinza automaticamente.

**Warning signs:** Componentes shadcn aparecem com cor de acento cinza (#71717a) em vez de magenta (#FF00FF).

### Pitfall 2: SelectFilter atual tem outside-click via overlay div — bits-ui Select resolve isso

**What goes wrong:** O `SelectFilter.svelte` atual usa um `<div style="position: fixed; inset: 0; z-index: 49">` para fechar o dropdown. Ao migrar para o Select do shadcn/bits-ui, esse padrão deve ser REMOVIDO — bits-ui gerencia dismiss automaticamente via Floating UI portal.

**Why it happens:** O padrão manual de overlay é um workaround; o Select do bits-ui renderiza em portal e usa event bubbling correto.

**How to avoid:** Remover o overlay div na migração. Testar que o dropdown fecha ao clicar fora.

**Warning signs:** Dupla camada de overlay causando z-index issues ou click events bloqueados.

### Pitfall 3: DataTable — shadcn Table fornece markup semântico, não lógica

**What goes wrong:** Confundir o `Table` do shadcn (que é apenas `<table>`, `<thead>`, `<tbody>`, `<tr>`, `<th>`, `<td>` com Tailwind classes) com uma solução completa de tabela. A lógica headless (`createTable`, `getSortedRowModel`) do `@tanstack/table-core` deve ser MANTIDA.

**Why it happens:** shadcn Table não inclui sorting, pagination, ou lógica de dados — é puramente presentational.

**How to avoid:** Continuar usando `@tanstack/table-core` para lógica. Substituir apenas os elementos HTML `<table>`, `<thead>`, etc. pelos subcomponentes shadcn equivalentes: `<Table>`, `<TableHeader>`, `<TableBody>`, `<TableRow>`, `<TableHead>`, `<TableCell>`.

**Warning signs:** Sorting para de funcionar; paginação quebra.

### Pitfall 4: ConfirmDialog — bits-ui Dialog vs native `<dialog>`

**What goes wrong:** O `ConfirmDialog.svelte` atual usa o HTML nativo `<dialog>` com `showModal()`. Ao migrar para Dialog do shadcn/bits-ui, a API é diferente: não existe mais `bind:this={dialog}` + `$effect(() => dialog.showModal())`. O bits-ui Dialog usa `bind:open={isOpen}` e renderiza via portal automaticamente.

**Why it happens:** Mudança de paradigma — imperativo (showModal) para reativo (bind:open).

**How to avoid:** Preservar a prop `open: boolean` da interface do ConfirmDialog. Dentro, usar `<Dialog.Root bind:open>` — bits-ui lida com showModal/close internamente. O backdrop e focus trap são automáticos.

**Warning signs:** Dialog não fecha ao clicar backdrop; Escape não funciona.

### Pitfall 5: $lib alias — svelte.config.js não declara $lib explicitamente

**What goes wrong:** O `svelte.config.js` atual só declara `$appmod` e `$core`. O alias `$lib` é provido automaticamente pelo SvelteKit (aponta para `src/lib/`). O shadcn init vai perguntar pelos aliases — confirmar `$lib` como `src/lib`.

**Why it happens:** `$lib` é built-in do SvelteKit, não precisa ser declarado manualmente.

**How to avoid:** Durante o `shadcn-svelte@latest init`, aceitar `$lib` como lib alias. Não adicionar `$lib: './src/lib'` manualmente ao `svelte.config.js` — SvelteKit já provê.

**Warning signs:** Erros de "Cannot find module '$lib/...'" em tempo de desenvolvimento.

### Pitfall 6: Componentes shadcn gerados com tw-animate-css não instalado

**What goes wrong:** Alguns componentes shadcn (Dialog, Select, DropdownMenu) usam animações que requerem `tw-animate-css`. Se não estiver instalado, as animações não funcionam silenciosamente.

**Why it happens:** tw-animate-css não é instalado automaticamente pelo CLI `add component`.

**How to avoid:** Instalar `tw-animate-css` e adicionar `@import "tw-animate-css"` no `app.css` no Wave 0.

**Warning signs:** Dialog abre sem animação de fade; Dropdown sem slide animation.

## Open Questions

1. **shadcn init interativo vs flags CLI**
   - What we know: O CLI pode ser rodado interativamente ou com flags. Não há documentação explícita de todas as flags para v4.
   - What's unclear: Se `npx shadcn-svelte@latest init` aceita `--tailwind-css` e `--components-alias` flags suficientes para ser não-interativo.
   - Recommendation: Rodar interativamente (o init é um processo único) e confirmar cada prompt manualmente. O planner deve documentar as respostas esperadas para cada prompt.

2. **`tw-animate-css` — incluído automaticamente pelo init?**
   - What we know: O CLI instala dependências base, mas `tw-animate-css` pode ou não ser incluído.
   - What's unclear: Se shadcn-svelte@latest init adiciona automaticamente o `@import "tw-animate-css"` ao `app.css`.
   - Recommendation: Verificar `app.css` após o init. Se não tiver `@import "tw-animate-css"`, adicionar manualmente + `npm install tw-animate-css`.

3. **DateRangeFilter → Calendar shadcn ou manter `input[type=date]`**
   - What we know: D-05 especifica "DateRangeFilter → usa Calendar do shadcn". O Calendar do bits-ui é um componente rico com seleção de range visual.
   - What's unclear: Se a API de prop `{ from: string, to: string }` (strings ISO date) é compatível com `DateValue` do `@internationalized/date` que o Calendar shadcn usa internamente.
   - Recommendation: O Calendar shadcn usa `DateValue` internamente mas pode ser wrappado para aceitar strings ISO. A conversão `string ↔ DateValue` é feita com `@internationalized/date` (já instalado). O planner deve especificar essa bridge explicitamente.
